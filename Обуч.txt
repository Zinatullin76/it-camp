ТЗ: система создания и проведения учебных материалов КТК
1. Цель

Разработать механизм, позволяющий инструктору создавать учебный контент без участия программиста, связывать его с технологическим оборудованием и физическим ядром тренажёра, назначать оператору и автоматически оценивать результат.

Система должна поддерживать полный цикл:

Технологическая документация → учебный материал → тест → практическое задание → сценарий → выполнение в SCADA → оценка → компетенция.

2. Основная концепция

В системе не должно быть отдельно существующих и не связанных между собой:

тестов;
заданий;
аварий;
сценариев;
оборудования.

Они должны быть связаны через учебный модуль и компетенции.

Пример:

Компетенция:
"Работа с насосным оборудованием"

             │
       ┌─────┴─────┐
       │            │
    Теория        Тест
       │            │
       └─────┬──────┘
             │
       Практическое
         задание
             │
       Сценарий отказа
             │
          Экзамен
3. Роли

В рамках данного функционала используются две роли.

Инструктор

Создает и редактирует учебный контент.

Оператор

Проходит назначенный контент и получает оценку.

Администратор управляет пользователями и доступами, но не создает технологический учебный контент.

4. Сущности системы

Разработать следующие сущности:

Course — курс

Module — учебный модуль

Lesson — теория

Question — вопрос

Task — практическое задание

Scenario — динамический сценарий

Equipment — технологический объект

Competency — компетенция

Assessment — результат прохождения

Связь:

Course
  ↓
Module
  ↓
Lesson
  ↓
Test
  ↓
Task
  ↓
Scenario
  ↓
Assessment
  ↓
Competency
5. Учебный модуль

Инструктор создает:

Новый модуль

Поля:

название;
описание;
цель обучения;
компетенция;
уровень сложности;
длительность;
связанное оборудование;
статус: черновик / опубликован.
Пример

Название:

Насос Н-1. Ввод в работу

Цель:

Научиться безопасно вводить насос Н-1 в работу и контролировать изменение технологических параметров.

Компетенция:

Работа с насосным оборудованием.

6. Теория

Внутри модуля инструктор создает теоретический материал.

Типы блоков:

текст;
изображение;
технологическая схема;
видео;
карточка оборудования;
выделенная область схемы;
интерактивная схема.
Пример
Насос Н-1

Назначение:
...

Расположение:
...

Контролируемые параметры:
...

Нормальное состояние:
...

Теория должна иметь связь с объектом технологической модели.

Например:

Урок
 ↓
Equipment: N-1

При открытии материала система может подсветить Н-1 на технологической схеме.

7. Конструктор тестов

Инструктор нажимает:

Добавить тест

Создает вопросы.

Поддержать типы:

Один ответ
Каково назначение Н-1?

○ Подогрев
● Подача сырья
○ Разделение
Несколько ответов
Какие параметры необходимо контролировать?

☑ Давление
☑ Расход
☐ Цвет
☑ Температура
Сопоставление
Насос       → Подача
Печь        → Подогрев
Колонна     → Разделение
Последовательность

Оператор расставляет операции в правильном порядке.

Выбор объекта на схеме

Система показывает технологическую схему.

Оператор должен нажать нужный объект.

8. Настройка оценки теста

Для каждого вопроса:

правильный ответ;
максимальный балл;
штраф за ошибку;
обязательность.

Для теста:

проходной балл;
количество попыток;
необходимость повторного прохождения.
9. Практическое задание

Практическое задание отличается от теста.

Тест проверяет:

Знает ли оператор?

Практическое задание проверяет:

Умеет ли оператор?

Создание задания

Инструктор задает:

Название

Ввод насоса Н-1 в работу

Цель

Выполнить ввод насоса в работу и обеспечить стабильную подачу сырья.

Начальное состояние
Н-1 — остановлен

Клапан — закрыт

Давление — нормальное

Расход — 0
Целевое состояние
Н-1 — работает

Клапан — открыт

Расход — в заданном диапазоне

Давление — в норме
10. Ограничения задания

Инструктор может определить запрещенные действия.

Например:

Нельзя:
запускать насос при закрытой линии.

Нельзя:
превышать допустимое давление.

Нельзя:
оставлять установку в промежуточном состоянии.

Это необходимо хранить как критерии оценки, а не просто текстовые подсказки.

11. Связь задания с физическим ядром

Это ключевое требование.

Фронтенд не должен самостоятельно моделировать технологический процесс.

Он только отправляет команды физическому ядру.

Например:

Оператор нажал "Пуск Н-1"

        ↓

Frontend

        ↓

Backend

        ↓

Physical Core

        ↓

Изменение состояния модели

        ↓

Backend

        ↓

SCADA
12. Сбор действий оператора

Физическое ядро и backend должны формировать журнал действий.

Например:

09:31:02
Открыт клапан V-12

09:31:07
Запущен Н-1

09:31:15
Расход начал увеличиваться

09:31:42
Давление стабилизировалось

Каждое действие должно иметь:

timestamp;
пользователя;
объект;
действие;
старое состояние;
новое состояние;
источник события.
13. Автоматическая оценка практики

После выполнения задания система сравнивает фактические действия с критериями задания.

Пример:

Критерий	Результат
Правильная последовательность	100%
Контроль параметров	100%
Время	90%
Ошибочные действия	80%
Безопасность	100%

Итог:

94/100

14. Сценарии

Сценарий — это последовательность событий, изменяющих состояние технологической модели во время занятия.

Пример

Сценарий: отказ Н-1

00:00
Нормальный режим

02:00
Снижение расхода

03:00
Тревога

04:00
Отказ Н-1

05:00
Оператор должен определить причину

06:00
Включение резервного насоса
15. Конструктор сценариев

Инструктор должен видеть timeline.

00:00       02:00       04:00       06:00
 │           │           │           │
 ▼           ▼           ▼           ▼
Норма      Изменение    Отказ       Контроль
           расхода       Н-1

Кнопка:

Добавить событие

16. Типы событий сценария

На MVP достаточно:

Изменение параметра
Давление → 1.5 МПа
Изменение состояния оборудования
Н-1 → Остановлен
Неисправность
Н-1 → Авария
Тревога
Создать Alarm
Изменение режима
Нагрузка → 80%
17. Важное правило сценария

Сценарий не должен содержать заранее прописанные изменения всех параметров процесса.

Например, после отказа Н-1 инструктор не должен вручную задавать:

расход = 0
давление = X
температура = Y.

Он задает:

Н-1 отказал.

А дальнейшие изменения рассчитывает физическое ядро.

Это принципиально важно для достоверности тренажёра.

18. Состояния сценария

Каждый сценарий имеет:

Черновик
↓
На проверке
↓
Опубликован
↓
Архивирован

Оператору доступны только опубликованные сценарии.

19. Сценарий должен иметь цель

Например:

Научиться распознавать отказ насоса по изменению технологических параметров и выполнять правильные действия по восстановлению режима.

Также задаются:

начальное состояние;
событие;
ожидаемые действия;
критерии успеха;
критические ошибки;
конечное состояние.
20. Экзаменационный сценарий

На основе обычных заданий и сценариев инструктор может создать экзамен.

Например:

Исходное состояние
        ↓
Нормальный режим
        ↓
Случайное событие
        ↓
Реакция оператора
        ↓
Второе событие
        ↓
Финальная оценка

В MVP достаточно предусмотреть структуру, но полноценную генерацию экзамена можно реализовать позже.

21. Связь с компетенциями

Каждое:

теоретическое занятие;
тест;
задание;
сценарий

может быть связано с одной или несколькими компетенциями.

Например:

"Работа с насосным оборудованием"

├── Теория Н-1
├── Тест Н-1
├── Пуск Н-1
├── Отказ Н-1
└── Экзамен

После прохождения система пересчитывает уровень компетенции.

27. Главный принцип архитектуры

Разработчикам необходимо зафиксировать следующее:

Учебный контент не должен быть жестко зашит во frontend.

Frontend должен получать структуру курса, задания, вопросы, сценарии и критерии оценки через API.

Например:

{
  "module": "pump_n1",
  "lesson": "...",
  "test": "...",
  "task": "...",
  "scenario": "...",
  "competencies": ["pump_operation"]
}

Конкретная реализация API зависит от вашего backend, но принцип должен сохраниться.

Самое главное для команды

Не программировать каждое учебное задание отдельно.

Нужно один раз создать универсальный механизм авторинга, в котором инструктор описывает:

что изучить → что проверить → что сделать → какое событие произойдет → что считается правильным → какую компетенцию это развивает.

А уже существующие backend + frontend + физическое ядро + SCADA обеспечивают выполнение этого описания.

Это даст вам очень сильную архитектуру для MVP: на презентации можно создать один сценарий в конструкторе, нажать «Опубликовать», зайти под оператором и тут же пройти созданное инструктором занятие.
