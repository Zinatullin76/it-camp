У тебя есть два существующих решения:

## Решение №1 — существующий MVP-проект

Это backend и ядро симулятора, которое уже было разработано ранее.

В нём необходимо сохранить и использовать существующие сильные стороны:

* Simulation Engine;
* Digital Twin;
* Equipment Models;
* Pump;
* Valve;
* Heat Exchanger / Heater;
* другие модели оборудования;
* Streams;
* Scenario;
* Scenario Registry;
* Simulation Time;
* Events;
* Alarms;
* Calculation Core;
* Thermodynamics;
* Solver;
* физические расчёты;
* существующие API;
* существующие тесты.

Главное преимущество этого проекта — архитектура и возможность реализовать реальную связанную физическую симуляцию технологического процесса.

## Решение №2 — HTML `avt4.html`

Это существующий HTML-интерфейс технологической схемы.

Из него необходимо сохранить и развить сильные стороны:

* визуальную технологическую схему;
* HMI-подобный интерфейс;
* визуальное отображение насосов;
* визуальное отображение клапанов;
* визуальное отображение другого оборудования;
* технологические линии / connections;
* возможность добавлять оборудование;
* возможность соединять оборудование;
* редактор схемы;
* сохранение схемы;
* загрузку схемы;
* JSON-представление схемы;
* визуальное состояние оборудования;
* удобное взаимодействие оператора;
* визуальную демонстрацию технологического процесса.

Главное преимущество HTML — он уже визуально показывает то, как должен выглядеть КТК для оператора и инструктора.

# ПРИНЦИП №1. ЕДИНЫЙ SOURCE OF TRUTH

Главное требование:

Frontend и Backend не должны иметь две разные модели технологической схемы.

HTML не должен самостоятельно решать физику.

Backend не должен хранить отдельную несовместимую схему.

Создай единый контракт:

```text
Equipment
Stream
Connection
Port
ProcessState
Command
Event
Alarm
```

Каждый элемент схемы должен иметь уникальный `id`.

Например:

```text
P-101
V-101
HX-101
C-101
```

Frontend использует этот ID.

Backend использует этот ID.

Digital Twin использует этот ID.

Physics Model использует этот ID.

Пример:

```json
{
  "id": "P-101",
  "type": "pump",
  "name": "Feed Pump"
}
```

Frontend:

```text
P-101
```

Backend:

```text
Pump(id="P-101")
```

Physics:

```text
PumpModel(id="P-101")
```

Это должен быть один и тот же объект Digital Twin.

---

# ПРИНЦИП №2. HTML СТАНОВИТСЯ HMI

Используй HTML как основу визуального интерфейса.

Но преврати его из standalone HTML в frontend, который получает состояние через Backend API.

Frontend отвечает за:

* визуализацию;
* взаимодействие;
* отображение схемы;
* отображение состояния;
* команды оператора;
* alarms;
* events;
* trends.

Frontend НЕ отвечает за:

* физические расчёты;
* гидравлический solver;
* термодинамику;
* расчёт материального баланса;
* расчёт энергетического баланса.

---

# ПРИНЦИП №3. BACKEND ОСТАЁТСЯ ФИЗИЧЕСКИМ ЯДРОМ

Сохрани существующий Calculation Core.

Не заменяй его mock-логикой.

Не делай:

```text
Valve 70%
→ Flow = 70
```

Сделай:

```text
Valve Opening
→ Valve Characteristic
→ Hydraulic Resistance
→ Solver
→ Flow
→ Pressure
→ Stream State
→ Downstream Equipment
```

Аналогично для насоса:

```text
Pump Start
→ Pump Model
→ Pump Curve
→ Pressure Head
→ Hydraulic Solver
→ Operating Point
→ Flow
→ Downstream Process
```

# ПРИНЦИП №4. ЕДИНАЯ ТОПОЛОГИЯ

Используй JSON-схему HTML как основу для определения топологии технологического процесса.

Пример:

```json
{
  "equipment": [
    {
      "id": "P-101",
      "type": "pump"
    },
    {
      "id": "V-101",
      "type": "valve"
    },
    {
      "id": "HX-101",
      "type": "heat_exchanger"
    }
  ],
  "connections": [
    {
      "from": "P-101",
      "to": "V-101"
    },
    {
      "from": "V-101",
      "to": "HX-101"
    }
  ]
}
```

Backend должен уметь преобразовать такую схему в Process Network:

```text
P-101
  ↓
Stream
  ↓
V-101
  ↓
Stream
  ↓
HX-101
```

После загрузки схемы должна существовать единая структура:

```text
Process Topology
      ↓
Digital Twin
      ↓
Simulation
```

# ПРИНЦИП №5. УПРАВЛЕНИЕ ОБОРУДОВАНИЕМ

Любое действие оператора должно проходить через Command Layer.

Пример:

```text
Operator
    ↓
START P-101
    ↓
Command API
    ↓
Command Validator
    ↓
Pump P-101
    ↓
Simulation Engine
    ↓
Calculation Core
    ↓
New Process State
    ↓
Frontend
```

Для клапана:

```text
Operator
    ↓
V-101 = 70%
    ↓
Command API
    ↓
Valve Model
    ↓
Hydraulic Solver
    ↓
Flow / Pressure Update
    ↓
Process State
    ↓
Frontend
```

Не разрешай frontend напрямую изменять Process State.

Frontend должен отправлять только команды.

# ПРИНЦИП №8. ДВА РЕЖИМА ИНТЕРФЕЙСА

Сделай два режима.

## Режим Instructor

Позволяет:

* создавать схему;
* добавлять оборудование;
* соединять оборудование;
* редактировать параметры;
* сохранять схему;
* загружать схему;
* создавать сценарий;
* задавать аварии;
* задавать начальное состояние;
* задавать ожидаемые действия.

## Режим Operator

Позволяет:

* видеть технологическую схему;
* видеть состояние оборудования;
* запускать / останавливать насосы;
* менять положение клапанов;
* управлять доступным оборудованием;
* видеть параметры;
* видеть alarms;
* видеть events;
* видеть trends;
* проходить сценарий.

Оператор НЕ должен иметь доступа к редактированию схемы и физической модели.

# ПРИНЦИП №9. ПЕРВЫЙ END-TO-END СЦЕНАРИЙ

Реализуй один полностью рабочий сценарий от начала до конца.

Например:

```text
P-101
  ↓
V-101
  ↓
HX-101
```

Сценарий:

```text
"Отказ насоса P-101"
```

Начальное состояние:

```text
P-101 = RUNNING
V-101 = 50%
Flow = NORMAL
Pressure = NORMAL
```

Через определённое время:

```text
P-101 = FAILURE
```

Оператор должен:

```text
1. Увидеть Alarm
2. Определить отказ
3. Остановить P-101
4. Запустить резервный насос P-102
5. Изменить положение V-102
6. Восстановить поток
```

Каждое действие должно пройти через реальный backend.

Например:

```text
START P-102
    ↓
Pump Model
    ↓
Hydraulic Solver
    ↓
Flow changes
    ↓
Pressure changes
    ↓
HX-101 receives new stream
    ↓
Process State changes
    ↓
UI updates
```

После завершения:

```text
Operator Actions
    ↓
Evaluation Engine
    ↓
Score
    ↓
Qualification Report
```

# КРИТИЧЕСКОЕ ТРЕБОВАНИЕ

В конце должен работать следующий сценарий:

```text
Оператор открывает КТК
        ↓
Видит технологическую схему из HTML
        ↓
Схема связана с Digital Twin
        ↓
Запускает сценарий
        ↓
Simulation Engine запускает процесс
        ↓
Возникает авария
        ↓
Оператор управляет насосом
        ↓
Оператор меняет открытие клапана
        ↓
Backend получает команды
        ↓
Физическая модель пересчитывает процесс
        ↓
Меняются Flow / Pressure / Temperature / Level
        ↓
Изменения отображаются на HMI
        ↓
Возникают Alarms / Events
        ↓
Все действия записываются
        ↓
Сценарий завершается
        ↓
Оператор получает Score
        ↓
Формируется Qualification Report
```

Если какое-либо действие пока не связано с реальной физической моделью, НЕ имитируй его молча.

Явно укажи:

```text

MOCKED
NOT IMPLEMENTED
```
