# ТЗ НА ПРОВЕРКУ ФИЗИЧЕСКОГО ЯДРА ЦИФРОВОГО ДВОЙНИКА ЭЛОУ-АВТ

## 1. Цель

Разработчики должны создать автоматический набор тестов, который доказывает корректность работы физического ядра цифрового двойника.

Проверяется не интерфейс, а физическая логика:

* topology технологической схемы;
* распределение давления;
* распределение расходов;
* материальный баланс;
* компонентный баланс;
* энергетический баланс;
* работа насосов;
* работа клапанов;
* сопротивление трубопроводов;
* параллельные и последовательные ветви;
* изменение режима при управляющем воздействии;
* изменение результата при изменении topology;
* обработка физически невозможных условий;
* сходимость solver;
* отсутствие скрытых fallback-значений.

---

# 2. Главный критерий приёмки

Недостаточно проверить:

```python
assert pump.flow == expected_flow
```

Каждый интеграционный тест должен проверять одновременно:

```text
TOPOLOGY
   ↓
BOUNDARY CONDITIONS
   ↓
PRESSURE FIELD
   ↓
FLOW FIELD
   ↓
EQUIPMENT EQUATIONS
   ↓
MASS BALANCE
   ↓
ENERGY BALANCE
   ↓
GLOBAL RESIDUAL
```

Расчёт считается успешным только если вся система физически согласована.

---

# 3. Формат теста

Каждый тест должен иметь:

```text
ID
Название
Цель
Входная схема
Входные параметры
Boundary conditions
Ожидаемый результат
Допустимая погрешность
Проверяемые инварианты
PASS/FAIL
Диагностика при FAIL
```

Все тесты должны запускаться автоматически через:

```bash
pytest
```

---

# 4. Уровни тестирования

Создать четыре уровня:

```text
L1 — unit tests
L2 — component tests
L3 — hydraulic network tests
L4 — full-system integration tests
```

---

# 5. L1 — Unit tests физических формул

Проверить отдельно:

* pipe pressure drop;
* Reynolds number;
* friction factor;
* velocity;
* valve pressure drop;
* pump characteristic;
* pump affinity laws;
* hydrostatic pressure;
* mass balance;
* energy balance;
* thermodynamic property calculations.

Каждая формула должна иметь минимум:

```text
normal case
boundary case
invalid input case
```

---

# 6. L2 — Тесты оборудования

## 6.1 Pipe

Проверить:

```text
Q ↑ → ΔP ↑
D ↑ → ΔP ↓
L ↑ → ΔP ↑
roughness ↑ → ΔP ↑
```

Также проверить:

```text
Q = 0 → ΔP_friction ≈ 0
```

для соответствующей модели.

---

## 6.2 Valve

Проверить:

```text
opening ↑ → resistance ↓ → Q ↑
```

и:

```text
opening = 0 → Q ≈ 0
```

если valve закрытый.

---

## 6.3 Pump

Проверить:

```text
pump speed ↑
→ pump head ↑
→ operating point changes
→ network flow changes
```

Проверить pump curve.

Проверить affinity laws в применимом диапазоне:

```text
Q ∝ N
H ∝ N²
Power ∝ N³
```

---

# 7. H01 — Pressure continuity

Схема:

```text
Pipe A ─┐
        ├── Junction ── Pipe C
Pipe B ─┘
```

Если junction не имеет собственной потери давления:

```text
P_A_out = P_B_out = P_C_in
```

Допуск:

```text
|ΔP| < 0.01%
```

FAIL при необъяснимом pressure jump.

---

# 8. H02 — Pressure drop accounting

Для:

```text
Source
 ↓
Pipe
 ↓
Valve
 ↓
Pipe
 ↓
Sink
```

проверить:

```text
P_source - P_sink
=
ΔP_pipe1
+
ΔP_valve
+
ΔP_pipe2
+
ΔP_static
```

Допуск:

```text
≤ 0.01%
```

---

# 9. H03 — Pressure loop

Создать замкнутый контур без насоса:

```text
      Pipe A
   ┌──────────┐
   │          ↓
Source      Junction
   │          ↑
   └──────────┘
      Pipe B
```

Проверить:

```text
ΣΔP_loop ≈ 0
```

Не должно существовать бесплатного pressure gain/loss.

---

# 10. H04 — Flow direction

Создать:

```text
A ── Resistance ── B
```

Case 1:

```text
P_A > P_B
```

ожидание:

```text
Q_A→B > 0
```

Case 2:

```text
P_A < P_B
```

ожидание:

```text
Q_B→A > 0
```

Это обязательный тест.

---

# 11. H05 — Flow reversal

Решить одну и ту же сеть при:

```text
P_A = 500 kPa
P_B = 300 kPa
```

и затем:

```text
P_A = 300 kPa
P_B = 500 kPa
```

Проверить:

```text
sign(Q_case_A) = -sign(Q_case_B)
```

---

# 12. H06 — Flow conservation

Для каждого junction:

```text
ΣQ_in - ΣQ_out = 0
```

Автоматически проверить **каждый узел**, а не только общий баланс схемы.

Допуск:

```text
≤ 0.01%
```

---

# 13. H07 — Series branches

Система:

```text
Source
 ↓
Pipe A
 ↓
Valve
 ↓
Pipe B
 ↓
Sink
```

Проверить:

```text
Q_A = Q_valve = Q_B
```

и:

```text
P_source > P_A > P_valve > P_sink
```

для пассивных элементов.

---

# 14. H08 — Parallel branches

Система:

```text
             ┌── R1 ── Sink A
Source ──────┤
             └── R2 ── Sink B
```

Проверить:

```text
Q_source = Q1 + Q2
```

Если:

```text
R1 < R2
```

то:

```text
Q1 > Q2
```

---

# 15. H09 — Изменение сопротивления ветви

Увеличить resistance ветви A.

Ожидается:

```text
Q_A ↓
Q_B ↑
```

при сохранении:

```text
Q_source = Q_A + Q_B
```

Проверяется реальное перераспределение flow.

---

# 16. H10 — Изменение downstream pressure

Для:

```text
             ┌── Branch A
Source ──────┤
             └── Branch B
```

увеличить:

```text
P_sink_B
```

Ожидается изменение:

```text
Q_B
P_junction
Q_source
```

и, при необходимости, `Q_A`.

Цель теста:

> доказать, что solver учитывает всю downstream network, а не только локальное сопротивление.

---

# 17. H11 — Parallel branch insertion

Case A:

```text
Source → R → Sink
```

Case B:

```text
             ┌→ R1 ─┐
Source ──────┤      ├→ Sink
             └→ R2 ─┘
```

При одинаковых pressure boundaries:

```text
Q_total_case_B > Q_total_case_A
```

если новая ветвь действительно создаёт дополнительный проводящий путь.

---

# 18. H12 — Valve closing

Закрыть valve:

```text
opening = 0
```

Ожидается:

```text
Q_valve ≈ 0
```

и **перерасчёт всей network**.

Если есть альтернативная ветвь:

```text
Q_alternative ↑
```

---

# 19. H13 — Pump operating point

Создать:

```text
Tank
 ↓
Pump
 ↓
Pipe
 ↓
Valve
 ↓
Tank
```

Проверить одновременно:

```text
pump characteristic
system resistance
operating flow
pump head
```

Ожидается:

```text
pump head(Q)
≈
system head(Q)
```

---

# 20. H14 — Pump speed perturbation

Case A:

```text
N = 100%
```

Case B:

```text
N = 110%
```

Проверить:

```text
Q_B ≠ Q_A
H_B ≠ H_A
```

и физически корректное направление изменений.

Главное:

> изменение speed должно изменить всю hydraulic network, а не только поле pump.

---

# 21. H15 — Source pressure perturbation

Увеличить:

```text
P_source
```

При прочих равных ожидать:

```text
driving ΔP ↑
Q ↑
```

для соответствующей пассивной системы.

---

# 22. H16 — Sink pressure perturbation

Увеличить:

```text
P_sink
```

Ожидается:

```text
driving ΔP ↓
Q ↓
```

для соответствующей конфигурации.

---

# 23. H17 — Pipe diameter perturbation

Увеличить диаметр.

Проверить:

```text
resistance ↓
pressure loss ↓
Q ↑
```

при фиксированном pressure boundary.

---

# 24. H18 — Roughness perturbation

Увеличить roughness.

Ожидается:

```text
friction ↑
ΔP ↑
Q ↓
```

при фиксированном pressure boundary.

---

# 25. H19 — Elevation

Создать два варианта:

```text
Δz = 0
Δz > 0
```

Проверить изменение static head:

```text
ΔP_static = ρgΔz
```

и соответствующее изменение flow.

---

# 26. H20 — Topology mutation

Исходная схема:

```text
Source → A → B → Sink
```

Удалить B через:

```python
scheme.remove_node(...)
```

Затем выполнить новый solve.

Проверить:

```text
network topology changed
hydraulic solution changed
old hydraulic state is not blindly reused
```

---

# 27. H21 — Добавление node/edge

Через:

```python
scheme.add_node(...)
scheme.add_edge(...)
```

добавить bypass.

Проверить изменение:

```text
pressure field
flow field
mass balance
```

---

# 28. H22 — Disconnected network

Создать две независимые подсистемы.

Ожидание:

```text
DISCONNECTED_NETWORK
```

или корректное независимое решение components.

Не допускается передача:

```text
pressure
flow
mass
```

между disconnected components.

---

# 29. H23 — Underconstrained network

Создать систему без достаточных boundary conditions.

Ожидается:

```text
UNDERCONSTRAINED_NETWORK
```

Запрещено:

```text
solver → Q=0 → CONVERGED
```

без объяснения.

---

# 30. H24 — Overconstrained network

Задать несовместимые:

```text
pressure boundary
+
flow boundary
```

Ожидается:

```text
OVERCONSTRAINED_NETWORK
```

или эквивалентный diagnostic.

Solver не имеет права молча менять пользовательские условия.

---

# 31. M01 — Global mass balance

Для всей схемы:

```text
Σmass_in - Σmass_out - accumulation = 0
```

Для steady-state:

```text
Σmass_in = Σmass_out
```

Допуск:

```text
≤ 0.01%
```

---

# 32. M02 — Node mass balance

Проверить каждый node:

```text
residual_node =
ΣQ_in - ΣQ_out
```

В результате solver должен вернуть:

```python
node_mass_residual_kg_s
```

---

# 33. M03 — Component balance

Для каждого компонента:

```text
component_in
=
component_out
```

Проверить минимум:

```text
water
hydrocarbon
salt
```

для соответствующей ELOU-модели.

---

# 34. E01 — Energy balance

Для каждого control volume:

```text
energy_in
+
heat_in
+
work_in
=
energy_out
+
heat_out
+
work_out
```

Допуск:

```text
≤ 0.1%
```

---

# 35. E02 — Heater

Для heater:

```text
Q = m Cp ΔT
```

Задать эталонный test case.

Проверить рассчитанный:

```text
heat duty
Tout
enthalpy
```

---

# 36. E03 — Heat exchanger

Проверить:

```text
hot-side energy balance
cold-side energy balance
total energy balance
pressure drop
```

Не допускается:

```text
Tout_hot > Tin_hot
```

без соответствующей физической модели.

---

# 37. T01 — Thermodynamic consistency

Для каждого state:

```text
P
T
composition
phase
density
enthalpy
```

должны быть взаимно согласованы.

---

# 38. T02 — Thermodynamic round trip

Рассчитать:

```text
P,T,composition → h
```

затем:

```text
P,h,composition → T
```

Проверить возврат к исходному `T`.

---

# 39. T03 — Flash balance

Проверить:

```text
Σx_i = 1
Σy_i = 1
0 ≤ vapor_fraction ≤ 1
```

и component mass balance.

---

# 40. GLOBAL-01 — Full network residual

После каждого hydraulic solve автоматически рассчитывать:

```python
node_mass_residual_kg_s
edge_pressure_residual_pa
```

и:

```python
global_residual
```

Solver не должен возвращать:

```text
CONVERGED
```

если residual выше заданного tolerance.

---

# 41. GLOBAL-02 — Pressure-flow causality

Создать baseline.

Последовательно изменить:

```text
source pressure
sink pressure
pump speed
valve opening
pipe diameter
roughness
elevation
```

Для каждого изменения записывать:

```text
before
after
ΔP
Q
```

и проверять ожидаемое направление изменения.

---

# 42. GLOBAL-03 — No NaN / Inf

После каждого solve автоматически проверять:

```python
math.isfinite(...)
```

для всех:

```text
pressure
flow
temperature
density
enthalpy
power
residual
```

Любой:

```text
NaN
Inf
```

→ FAIL.

---

# 43. GLOBAL-04 — No silent fallback

Тест специально должен создавать ситуацию, в которой solver не может получить решение.

Проверить:

```text
solver_status != CONVERGED
```

и наличие diagnostic.

Запрещено возвращать:

```text
0
default value
previous state
```

и объявлять это физическим решением.

---

# 44. GLOBAL-05 — Determinism

Один и тот же input:

```text
same scheme
same parameters
same boundary conditions
```

должен давать одинаковый результат.

Проверить минимум 100 повторных запусков.

Результаты должны совпадать в пределах numerical tolerance.

---

# 45. GLOBAL-06 — Perturbation tests

Для ключевых параметров автоматически выполнять:

```text
x - 10%
x
x + 10%
```

и проверять физический знак производной:

```text
dQ/dP_source > 0
dQ/dP_sink < 0
dQ/dvalve_opening > 0
dQ/droughness < 0
dQ/ddiameter > 0
```

для соответствующих конфигураций.

---

# 46. GLOBAL-07 — Regression tests

Каждый обнаруженный физический баг должен превращаться в regression test.

Формат:

```text
bug_id
input_scheme
input_parameters
expected_physics
previous_failure
fixed_behavior
```

После исправления баг не должен появляться снова.

# 49. PASS / FAIL

## PASS

Тест считается PASS только если:

```text
✓ expected physical behavior
✓ mass balance
✓ pressure balance
✓ equipment equations
✓ boundary conditions
✓ solver convergence
✓ numerical residual
```

соответствуют установленным tolerance.

## FAIL

Тест FAIL при любом из:

```text
✗ неправильное направление flow
✗ нарушение mass balance
✗ необъяснимый pressure jump
✗ неправильная реакция на valve
✗ неправильная реакция на pump
✗ неправильное распределение parallel flow
✗ нарушение energy balance
✗ NaN/Inf
✗ silent fallback
✗ игнорирование topology
✗ ложный CONVERGED
```

# 51. Критические блокеры

Следующие ошибки автоматически блокируют приёмку физического ядра:

### BLOCKER-1

Нарушается mass balance.

### BLOCKER-2

Pressure field не согласуется с hydraulic equations.

### BLOCKER-3

Расход не перераспределяется между parallel branches.

### BLOCKER-4

Изменение pump speed не меняет network operating point.

### BLOCKER-5

Изменение valve не меняет соответствующую network.

### BLOCKER-6

Solver объявляет `CONVERGED` при большом residual.

### BLOCKER-7

Solver скрывает невозможность решения через default values.

### BLOCKER-8

Изменение topology не приводит к пересчёту физического состояния.

### BLOCKER-9

Появляются NaN/Inf.

### BLOCKER-10

Нарушается global energy/material balance в эталонных случаях.

---

# 52. Финальная приёмка

Физическое ядро принимается только при выполнении всех условий:

```text
100% critical tests PASS
100% BLOCKER tests PASS
0 NaN/Inf
0 silent fallback
0 unresolved mass-balance violations
0 unresolved pressure-balance violations
0 false CONVERGED
```

Для остальных тестов допускается наличие известных ограничений, но каждое такое ограничение должно быть:

```text
явно документировано
```

и иметь:

```text
issue ID
severity
description
planned fix
```

---

# 53. Главный интеграционный тест

Финальная проверка должна запускать одну полную модель:

```text
FEED
  ↓
PUMP
  ↓
ELOU
  ↓
PREHEATER
  ↓
FURNACE
  ↓
ATMOSPHERIC COLUMN
  ↓
PRODUCT NETWORK
```

В ней выполнить последовательность:

```text
1. Baseline solve
2. Increase pump speed
3. Close valve
4. Change feed flow
5. Change feed temperature
6. Change downstream pressure
7. Add/remove bypass
8. Repeat solve
```

После каждого шага проверить:

```text
PRESSURE
FLOW
MASS
COMPONENTS
ENERGY
TEMPERATURE
EQUIPMENT
TOPOLOGY
RESIDUALS
```

Финальный результат должен доказывать:

> изменение одного физического параметра приводит к причинно связанному изменению всей связанной технологической сети и при этом сохраняются физические балансы.

# 54. Требование к разработчикам

Результатом работы должны быть **не только тесты**, но и:

1. каталог тестовых схем;
2. автоматический pytest-suite;
3. эталонные expected results;
4. tolerance для каждого класса расчёта;
5. machine-readable diagnostics;
6. regression suite;
7. итоговый acceptance report;
8. список известных ограничений физической модели.

### Запрещается

Считать физическое ядро проверенным на основании:

```text
✓ приложение запускается
✓ схема открывается
✓ насос показывает расход
✓ значения выглядят реалистично
✓ интерфейс не падает
```

### Проверка должна доказывать физическую согласованность:

```text
                 ┌──────────────┐
                 │  TOPOLOGY    │
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │ PRESSURE     │
                 │ FIELD        │
                 └──────┬───────┘
                        ↓
                 ┌──────────────┐
                 │ FLOW FIELD   │
                 └──────┬───────┘
                        ↓
              ┌─────────┴─────────┐
              ↓                   ↓
       MASS BALANCE        ENERGY BALANCE
              ↓                   ↓
              └─────────┬─────────┘
                        ↓
                EQUIPMENT MODELS
                        ↓
                   RESIDUALS
                        ↓

```
