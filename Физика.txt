# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## Доработка физического ядра цифрового двойника ЭЛОУ–АВТ

**Версия:** 1.0
**Статус:** к разработке
**Назначение:** физический simulation core для цифрового двойника и операторского тренажёра подготовки нефти ЭЛОУ–АВТ.

---

# 1. Цель проекта

Доработать существующее физическое ядро без переписывания с нуля.

Необходимо превратить текущий набор моделей:

* P&ID scheme;
* Stream;
* thermodynamics;
* hydraulics;
* equipment;
* balances;
* SimulationEngine;

в **единую согласованную физическую систему**, в которой:

1. топология процесса задаётся через P&ID graph;
2. конфигурация оборудования отделена от runtime physics state;
3. все единицы измерения однозначны;
4. существует один thermodynamic authority;
5. гидравлическая сеть реально решается внутри `SimulationEngine`;
6. насосы работают через pump/system curve;
7. pipe/valve/equipment pressure losses входят в общий hydraulic solve;
8. mass/component/energy balances контролируются автоматически;
9. ошибки solver не маскируются;
10. каждый simulation step имеет физический статус;
11. результаты воспроизводимы;
12. существующие модели оборудования сохраняются и улучшаются, а не заменяются фиктивными упрощениями.

---

# 2. Текущее состояние

В проекте уже существуют:

```text
ProcessScheme
SchemeNode
SchemeEdge
load_scheme()
save_scheme()

Stream

PengRobinsonThermodynamics

VLE

Pump
Valve
Tank
HeatExchanger
Furnace
ELOU
DistillationColumn

pressure_drop
line_hydraulics

SimulationEngine

balance_checker
```

Имеется хороший MVP-фундамент.

Однако физические компоненты сейчас соединены неполностью.

Основные проблемы:

* гидравлический solver существует отдельно от engine;
* в `SimulationEngine` отсутствует полноценная интеграция hydraulic solve;
* насос не имеет полноценной зависимости `ΔP = f(Q, speed)`;
* flow units неоднозначны;
* pipe hydraulics не является частью общего network solve;
* branch distribution частично эвристическое;
* отсутствует static head;
* NPSH/cavitation реализованы упрощённо;
* существуют две VLE/thermodynamic реализации;
* fallback некоторых solver'ов может скрывать физическую ошибку;
* `SchemeNode.params` слишком свободный;
* runtime state недостаточно отделён от scheme configuration;
* отсутствует полноценный regression test suite.

# 3. Главный архитектурный принцип

Разделить систему на четыре независимых слоя:

```text
                 P&ID CONFIGURATION
                         │
                         ▼
                  ProcessScheme
                         │
                         ▼
                  SchemeValidator
                         │
                         ▼
              Typed Equipment Config
                         │
                         ▼
┌─────────────────────────────────────────────┐
│                 PHYSICS CORE                │
│                                             │
│ Thermodynamics ←→ Hydraulics ←→ Equipment  │
│        │                │             │     │
│        └──────── Balances ────────────┘     │
└──────────────────────┬──────────────────────┘
                       ▼
                  PhysicsState
                       │
                       ▼
                Validation Layer
                       │
                       ▼
                SimulationResult
```

## Запрещается

Хранить runtime physics state в `ProcessScheme`.

Например `SchemeNode.params` не должен во время симуляции содержать:

* текущий pressure;
* текущий temperature;
* текущий flow;
* current level;
* phase;
* duty;
* runtime composition.

`ProcessScheme` — это конфигурация и topology.

`PhysicsState` — текущее состояние процесса.

# 19. Pump model — критически важно

Переделать Pump.

Вместо:

```python
delta_p = fixed_value * speed²
```

реализовать:

```text
ΔP_pump = f(Q, speed)
```

Минимальная модель:

```text
ΔP(Q,N)
```

например через:

```text
H0(N) - a(N) Q²
```

или через таблицу pump curve.

---

# 20. Pump curve

Создать:

```python
class PumpCurve:
    def pressure_rise(
        self,
        volumetric_flow_m3_s: float,
        speed_fraction: float,
    ) -> float:
        ...
```

Обязательная проверка:

```text
Q = 0
```

должна давать dead-head pressure.

При увеличении Q:

```text
pump pressure generally decreases
```

в пределах рабочей характеристики.

---

# 21. Pump/system operating point

Hydraulic solver обязан искать рабочую точку:

```text
pump pressure rise
=
system pressure requirement
```

То есть одновременно решаются:

```text
Pump curve
System curve
```

Результат:

```text
operating_flow
operating_pressure
```

---

# 22. Pump affinity laws

При наличии speed control использовать:

```text
Q ∝ N
ΔP ∝ N²
Power ∝ N³
```

в пределах применимости модели.

Speed должен влиять на pump curve, а не только искусственно масштабировать конечный flow.


Ввести:

```text

```

```text

```

```text
mass_flow = density × volumetric_flow
```

# 24. Hydraulic network solver

Для последовательной линии:

```text
P_source
+
ΔP_pump(Q)
-
ΣΔP(Q)
-
P_sink
=
0
```

решать Q численно.

Для branch network:

решать одновременно:

```text
mass conservation
+
pressure equality at junction
+
branch pressure equations
```

Нельзя распределять branch flows только пропорционально весам.

---

# 25. Branch solver

Требуется заменить эвристический подход:

```text
share = q * weight / total_weight
```

на решение:

```text
Q_branch
```

для каждой ветки из её hydraulic resistance.

Условие:

```text
ΣQ_branch = Q_parent
```

и для каждой ветви:

```text
P_junction - P_sink
=
ΔP_branch(Q_branch)
```

---

# 26. Удалить искусственный minimum flow

Запрещено использовать физически необоснованные конструкции вида:

```python

```

для определения flow.

Если сопротивление не определено:

```text

```

а не искусственный расход.


### R02 — Normal steady state

Проверить:

```text
mass balance
energy balance
hydraulics
thermodynamics
```

### R03 — Valve throttling

Уменьшение открытия должно привести к:

```text
flow ↓
upstream pressure ↑
```

### R04 — Pump speed increase

Должно привести к:

```text
pump head ↑
flow ↑
```

если system allows.

### R05 — Pump speed reduction

Обратный эффект.

### R06 — Blocked downstream

Проверить:

```text
flow ↓
upstream pressure ↑
```

без появления отрицательных физических величин.

### R07 — Solver failure

Создать намеренно плохой operating condition.

Проверить, что:

```text
status = DEGRADED / FAILED
```

и ошибка не маскируется.

# 48. Acceptance criteria

Работа считается выполненной, если:

## Scheme

* JSON загружается;
* JSON сохраняется;
* round-trip не меняет структуру;
* invalid topology обнаруживается.

## Thermodynamics

* один authoritative backend;
* flash стабилен;
* phase state определён;
* enthalpy inversion проходит regression tests.

## Hydraulics

* Engine реально вызывает hydraulic solver;
* pipe resistance входит в solve;
* valve resistance входит в solve;
* pump curve входит в solve;
* equipment pressure drop входит в solve;
* static head учитывается;
* branch network решается через pressure/flow equations;
* flow units однозначны;
* нет silent overwrite.

## Balances

На всех regression cases:

```text
mass residual       < tolerance
component residual  < tolerance
energy residual     < tolerance
```

## Solver

Каждый solver возвращает:

```text
status
iterations
residual
diagnostics
```

## Simulation

`engine.step()` возвращает:

```text
PhysicsState
HydraulicResult
SolverStatus
Diagnostics
BalanceStatus
```

# 51. Критерий качества цифрового двойника

После доработки система не должна создавать ситуацию:

```text
solver failed
     ↓
эвристика придумала значение
     ↓
значение показано оператору
     ↓
оператор считает его физическим
```

Допустим только путь:

```text
physical equations
       ↓
solver
       ↓
converged
       ↓
validated balances
       ↓
PhysicsState
```

или:

```text
solver failure
       ↓
DEGRADED / FAILED
       ↓
diagnostic
       ↓
явно маркированный результат
```
